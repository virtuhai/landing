# AI Engine — Vendor Decision & Data Residency

**Статус:** Open question, потребує вирішення до вибору вендора (перед Stage D core-api).

---

## Поточне рішення (Stage 3, до фінансування)

**Hosted API (Anthropic/OpenAI) з першого дня.**

Обґрунтування — чисто економічне на pre-revenue стадії:
- Self-hosted модель (Llama/Mistral через vLLM) вимагає GPU-інстанс, що коштує 24/7 незалежно від навантаження.
- Поточний обсяг запитів — одиниці на добу (демо, тестування). Hosted API на pay-per-request econimics виграє з великим запасом, поки трафік не зросте на порядки.
- Vendor lock-in мінімальний: промпти й бізнес-логіка живуть у `core-api/app/ai_engine/`, сам виклик моделі — тонкий шар, що замінюється без переписування продукту.

**Це рішення НЕ остаточне.** Переглядається за будь-якою з двох умов нижче — обидві незалежні одна від одної.

---

## Open Question: Data Residency

**Питання:** чи вимагатимуть Brave1/оборонні партнери, щоб координати загроз і сенсорні фіди (Threat/TrackedObject/Sensor дані) не покидали контрольовану інфраструктуру?

**Чому це питання, а не формальність:**
- Продукт позиціонується під Brave1/defense-сектор — саме той клас клієнтів, де data residency зазвичай не побажання, а контрактна/регуляторна вимога.
- Hosted API (Anthropic/OpenAI) означає, що дані загроз (координати дронів, сенсорні звіти, reasoning з `Threat.reasoning`) фізично покидають інфраструктуру VIRTUHAI й потрапляють до інфраструктури вендора при кожному AI-виклику.
- Якщо відповідь "так, дані мають лишатись всередині" — hosted API стає **повним блокером**, не оптимізацією для пізнішого етапу. Рішення про self-hosted доведеться приймати ДО того, як стане економічно вигідніше, а не "коли зросте трафік".

**Статус з'ясування:** не з'ясовано. Питання зафіксоване тут навмисно без відповіді — щоб не забути підняти його перед реальним підписанням контракту з hosted-вендором чи входженням у Brave1-програму.

**Дія:** підняти це питання явно на першому предметному контакті з Brave1 чи будь-яким оборонним партнером, до підписання будь-якого data processing agreement з Anthropic/OpenAI.

---

## Тригери для переходу на self-hosted (Llama/Mistral + vLLM)

Перехід стається обов'язковим, а не опціональним, за будь-якою з умов:

1. **Регуляторна:** Brave1/оборонний партнер підтверджує вимогу data residency (питання вище).
2. **Економічна:** обсяг запитів зростає настільки, що вартість hosted API per-request перевищує вартість утримання GPU-інстансу 24/7. Поріг залежить від поточних цін вендорів на момент оцінки, не фіксується тут заздалегідь.

Обидва тригери незалежні — перший може спрацювати значно раніше другого, і саме тому рішення "hosted зараз" не повинно сприйматись як довгострокова архітектурна константа.

## Rule Engine vs AI — розподіл відповідальності

Не кожна threat-оцінка потребує LLM. Явний розподіл, щоб уникнути "AI на все" за замовчуванням:

**Rule engine (детермінований, без LLM-виклику):**
- Прості порогові сценарії: швидкість/висота/траєкторія об'єкта відповідає відомому патерну (наприклад, різке зниження висоти поблизу `ProtectedSite` — вже перевірено на прикладі `assess_threat()` у Stage C).
- Швидше, дешевше, повністю прозоре для audit (`Threat.assessed_by = rule_engine`, `reasoning` — сама умова, що спрацювала).

**AI (`Threat.assessed_by = ai`):**
- Non-trivial сценарії: множинні сигнали одночасно, суперечливі дані з різних сенсорів, потреба в природномовному `reasoning` для людини-оператора.
- Дорожче й повільніше за rule engine — використовується вибірково, не як дефолтний шлях для кожної оцінки.

Обидва шляхи вже сумісні з поточною моделлю даних (`AssessedBy` enum у `app/models/enums.py`) — жодних змін схеми не потрібно для впровадження цього розподілу.

## Наступні кроки (Stage D)

1. З'ясувати data residency питання (див. вище) — паралельно з технічною роботою, не блокер для старту Stage D.
2. Реалізувати `app/ai_engine/` — тонкий шар виклику hosted API, ізольований від бізнес-логіки rule engine.
3. Визначити конкретні тригери rule engine → AI escalation (які саме патерни/невизначеність тригерять AI-виклик замість чистого rule engine).
4. Rule engine — реалізувати першим (не залежить від vendor-рішення, не залежить від data residency питання).
